# 串行批次、下游优先与明确交接

当搜索候选不断增加、正文/评论/媒体尚未处理时，使用 `scripts/xhs_batch.py` 管理批次。它复用现有 `Project.resume`，不改变采集、归属和完成语义，不替代 Codex 阅读。原有 `xhs_project.py resume` 和单项命令继续可用。

## 先查看，再推进

```bash
python "$XHS_SKILL/scripts/xhs_batch.py" --project "$XHS_PROJECT" plan
python "$XHS_SKILL/scripts/xhs_batch.py" --project "$XHS_PROJECT" work --run "$XHS_RUN" --units 10 --max-seconds 1800
```

`plan` 用只读 SQLite 检查，不创建项目、改任务或读取凭据。它报告项目 STOP；真正运行仍会检查 run 与同账号 STOP。若存在 STOP，先按运行说明处理实际访问原因；此脚本没有清除 STOP 或自动换会话的能力。`--max-seconds` 是两项工作之间检查的墙钟预算，不会在一个已开始的 HTTP/浏览器工作单元中间强行截断。

`work` 自动衔接普通预算断点，默认每批最多 10 单元/300 秒，总计最多 12 批/1800 秒；可用 `--batch-seconds`、`--max-batches` 调整。到审读阈值、搜索页组结束、真正缺口或 STOP 时交接。`run` 仍保留单批兼容模式。如何区分 Codex 工作与用户操作，见[自主运行](autonomy.md)。

默认顺序：

- 已纳入范围的正文、已创建的一级评论、相关作者和浏览器回复按项目优先级处理；浏览器通常等对应一级评论枚举完成再展开。
- 正文待采要有 `title_scope_review`、`scope_included` 或相应人工范围决策。旧搜索导入的 `needs_triage=false` 本身不能证明已筛选。作者主页的生活笔记仍先交接主题筛选。
- 累积 20 个采集完成但文字分析待处理的任务时，暂停新增正文和搜索并交接审读。若积压正文带有人工“文字已读”记录、该记录的正文哈希仍与当前文档一致，且相关媒体尚未核完，已入队的评论、浏览器回复和作者检查仍可独立推进；当其它未读文字任务也达到 20 个时，必须返回 `handoff`。Codex 读完并记录审核；媒体未读的旧正文始终保留待审状态，不能为继续队列假报已读。
- 没有可执行下游时，未审文字、待筛选卡片、媒体和普通缺口先交接；不会不断搜索扩词来稀释这些缺口。
- 只有这些下游工作已处理，才开始新搜索页组。同一 query+sort 默认连续最多 5 页，再交接新候选或轮换其他查询。组内状态跨普通批次保持，减少交错查询导致搜索上下文过期的重复预热。页组预算不代表搜到末尾，真实结束仍必须由平台响应确认。

## 关键线索可以显式优先

媒体未读或某个旧楼层受阻不应永久挡住已确认有用的作者、评论或正文。Codex 阅读现有来源后，可创建只包含真实任务 ID 的 JSON 数组，按顺序补这些缺口：

```bash
python "$XHS_SKILL/scripts/xhs_batch.py" --project "$XHS_PROJECT" plan --task-list '/已核对的优先任务.json'
python "$XHS_SKILL/scripts/xhs_batch.py" --project "$XHS_PROJECT" run --run "$XHS_RUN" --task-list '/已核对的优先任务.json' --units 5
```

显式队列优先于全局待审/媒体阈值，分页任务持续到平台结束或本批预算；因此应使用小批并在每批后审读新增文字。它不改变原任务优先级/状态，不清除 STOP，不执行 blocked/excluded/已完成任务，也不自动批准 `needs_triage=true` 的作者笔记。显式选择 browser 时，若已有同帖一级评论任务仍 pending，会先续其分页；一级评论 blocked 则保留缺口并交接，不借 browser 调度自动 retry。任务列表只是本批优先顺序，不是新的研究排除条件；未列出的任务仍在项目报告中。

正文的图片仍未读、但已确定值得查评论时，可先用项目 `review --decision include` 标记范围；它创建评论与浏览器任务，保留正文的未审状态。若 Codex 已实际读完当前文字，可通过 `--annotations` 显式保存 `{"text_review":{"document_id":"note:实际noteID","text_sha256":"当前documents.text按UTF-8计算的SHA-256"}}`。只有同一笔记文档及当前文字哈希均吻合，批次才能把这项暂列为媒体待核，允许独立后续工作；没有该记录或文字后来改变，仍计入未读文字阈值。不能因为有图片、正文短或摘要看似读过就生成该标记。标记不改变正文 review_status，也不表示媒体已读或病例已核实。脚本不会自己做这些判断。媒体另交给 `xhs_media.py` 和实际视觉/音频核查，再 `import-media`；未下载、未听校或转写可疑不能算完成。

## 从详情切回搜索时的可见性核查

恢复搜索前，先核当前登记的 owned 搜索标签、同账号和准确 query。路径比较使用已有 target_path 等归一化方式兼容合法尾斜杠；query 和身份仍须准确匹配。原标签只是后台、无访问警告且没有其他使用者占用时，可普通选择该标签一次并核 visible=true，再运行采集；不导航到其他页面，不清故障或停止记录。预检失败时先处理结果，不接着执行依赖该预检的采集命令。同一连续批次角色未切换时，不为每个动作重复激活。

几何滚动不等于内容新增；分别核游标、首尾笔记ID和唯一增量。预算结束、重复卡窗或几何到底均不充当平台末尾。批次工作单元和保存快照数量也可能不同：正常预滚动捕获会单独落源。审读前核该任务全部未审哈希，不能只取 unit 日志或相加 new_note_ids 而漏掉首源；已审同版来源只复用原记录，不重复计新阅读量。

## 显式多帖清单的同帖接续

多帖优先清单保留各帖原顺序。若刚审读完同帖的10个单元，仍要继续该帖，可为下一批生成只含该帖 roots/replies 真实任务ID的临时清单；原多帖清单和其余待办保留。单scope的已审范围才能按现有调度规则获得新配额，不能直接改 group_units、故障、游标或审读状态。

出现 processed_units=1 的审读交接时，先查真实增量和剩余范围。它可能已读到新加载的大量文字，不等于采集失败；先实际审读新哈希。若需要同帖连续推进，再用上述临时清单接续，避免无条件反复运行同一混合范围清单。下一批仍最多10个采集单元后实际审读；Codex负责适时轮换其他可执行帖子，不将临时清单变成永久排除范围。

## 大记录的输出与数字澄清

大型评论任务的 `native record` 返回可能包含整个 `task.payload` 和累计评论树。完整返回写入独立结果文件；对话中只提取 `event_id`、任务状态和本次变化，不打印整个返回，也不为了缩短输出再执行一次写入。原始快照和完整回执继续保留，精简索引关联原文件与 SHA。增量审读仍读取所有新增或实质修改内容及必要上下文；省输出不能代替阅读。

平台显示评论数与已发现的唯一 CID 数分开统计。已有有效的当前可见文字 END 凭据时，计数差异另列原因未知的缺口；不补出未见评论，不猜删除或隐藏，也不把显示总数当已读数。核对 `remainingThreads` 等字段时遵循相应采集格式：列表型字段检查空列表，计数字段检查零；类型不符、缺失或 null 保留核查缺口，不直接当零，也不改写原快照来凑格式。

只纠正旧摘要数字或措辞时，追加引用原快照和旧事件的离线澄清；使用 `action=offline`、`outcome=offline`，并保持 `content_observed=false`、`reviewed=false`、`complete=false` 及全部 UI 核验声明为 false。澄清不产生新的采集、语义阅读或完成凭据，不重开有效 END，不重置 bridge 哈希、故障或重试次数；提交前后核这些状态未变。正文、评论附件、视频和作者后续各自保留未完成范围。

## 跨会话节奏、锁与中断

多个研究共用账号时，`run/work` 的每个采集单元先进入账号级 FIFO 队列，再取得项目、会话及账号锁。候选筛选、离线阅读和报告仍各自推进；网络工作轮流执行，不承诺两个浏览器同时操作同一页面。排队、旧版本采集占锁时返回 `waiting/shared_account_queue` 进度，无需用户批准。等待消耗本批时间预算，但不消耗采集单元，不推进页码、不标记阅读完成；`work` 在总预算内接续等待。

排队每秒检查会话/账号 STOP 和本项目暂停文件，取得锁后再次核查。持票进程退出后，下一位通过内核文件锁确认失效票据再清理；绝不因此删除旧 `.collection.lock`、账号锁或 STOP。旧版任务不参加公平轮转，但仍受原账号锁保护，升级侧等待其释放。所有研究使用升级版 `run/work` 后才能享有完整的 FIFO 协调。项目内 `media/` 的真实下载也逐项加入同一队列，每次最多等待600秒；本地已有文件和模拟下载不联网、不排队。独立于项目的旧媒体目录及直接单项采集仍用原账号锁，不自动获得 FIFO 公平性。媒体等候超时或暂停会退出并保留断点，不将未下载内容标作完成。

新的命令会加载新版；已经运行的旧进程不会热更新。研究标签页丢失、会话已关闭和访问限制不是普通排队问题，仍按原恢复流程处理；不要以排队升级为由重建会话绕过停止记录。

本地审读或导入短暂持有同一项目锁时，采集队列也自动等待，不作为采集失败或用户授权事项。等待仍受时间预算、暂停和 STOP 约束；项目数据损坏等其他异常不按占锁重试。直接单项命令仍可返回占用错误，调用方应等待现有写入完成后从断点继续，不删除锁。

检查项目停止状态时，SQLite 若被本地写入暂时锁住，队列同样等待；读不到停止状态不能视为允许采集。仅等待 SQLite 明确报告的 BUSY/LOCKED，期间仍检查账号 STOP、用户暂停及预算；释放后重新确认项目 STOP，数据库损坏、结构错误及其他故障保留原错误。

长期并行的两个研究应各自拥有 run 和固定研究标签，绑定相同账号键后共享 FIFO 队列。这样某个研究正常 cleanup 只清理自己拥有的浏览器和临时凭据。队列也兼容现有共用 run，但不能保证一个项目主动关闭共用会话后另一个仍能采集；遇到该情况保存断点，不自动重开。新建各自 run 必须等旧访问状态已核实恢复，不能用会话隔离绕过账号 STOP。

批次状态和追加日志位于项目 `batch/state.json`、`batch/journal.jsonl`；不保存登录凭据。当前搜索页组和进行中的任务都保留。每次收集仍由项目锁、run 锁与共享账号锁保护，不提高并发。

默认每个工作单元完成后至少间隔 10 秒（`--interval` 可选择 3..600 秒）。下一可运行时间在共享账号目录的 `batch-pacing.json` 中，在开始前即持久化；另一个项目/新 run 的批次不能重置这个间隔。底层 API 原有逐请求间隔仍有效。这里控制的是批次工作单元，浏览器单元内部依然遵循原展开预算，不声称能防止或解除平台限流。

普通 `checkpoint/unit_budget` 或 `checkpoint/time_budget` 只表示本批结束，`work` 自动接续。`work_budget` 是整轮断点，Codex 继续处理；`handoff` 是 Codex 的原文审读、主题筛选或媒体工作，不是请求用户批准。交接保存 `actor=codex`、`requires_user_input=false` 及任务/数量，真正登录或权限问题须先诊断。只有没有待办和待审时才返回 `scope_processed`，仍只指项目规定的已知范围。

按 Ctrl-C 或通过 `--checkpoint-file '/暂停标记路径'` 留断点。日志包含进行中的任务；重启仍由原 `Project.resume` 恢复已保存但尚未入库的原始快照。若进程被强制结束导致旧 run 锁残留，先检查对应进程与现场，不能直接当作访问 STOP 清除。

遇登录失效/验证码/访问限制马上停止。`run` 遇普通缺口也交接；`work` 仅对结构化、无响应的指定传输超时作一次持久化受限重试，其余缺口由 Codex 检查或修复，见[重试边界](autonomy.md)。继续时保留旧原文与失败记录。明确优先队列能跳到其他已授权可访问内容，但不得在账号 STOP 存在时运行。普通审读或单帖缺口不触发 cleanup。
